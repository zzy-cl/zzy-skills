# 技术文档写作

一套经实战校准的写作规范。产出目标：**体裁正确、每句话都挂在读者的动作上、事实可溯源**的文档。

核心认知（所有规则的出处，执行中拿不准时回到这里）：

- 文档的价值 = 它改变读者多少动作和判断；读者的成本按**每行的认知税**结算，不按总字数。
- 文档的失败几乎总是"多"而不是"缺"：误删 ≈ 一人次提问，误留 = 每个读者每次阅读付费。**偏向删除。**
- 文档是真相的缓存：必须可溯源、标注时效、能让失效被发现。

**技能根目录**：本文件所在目录即技能根目录，`references/` 与 `scripts/` 相对它定位。不同 Agent 加载技能的机制不同（有的自动注入本文件，有的按指令手动读取）；路径解析失败时，按此相对关系直接读取文件。

## 入口判断

| 用户意图 | 路径 |
|---|---|
| 新写一篇 | 走完整工作流（下文第 1–6 步） |
| 重写/梳理已有文档 | 先读 `references/antipatterns.md`，按其诊断旧文；再从第 1 步走完整工作流（事实仍需重新核对，不能沿用旧文说法） |
| 评审一篇文档 | 只做第 2 步的事实核对 + 第 6 步的 checklist，输出问题清单（按"致命/应修/建议"分级），不代用户改写 |
| 压缩一篇文档 | 只做第 5 步：逐句判"挂在哪个动作上"，输出删减对照表，保留原文事实不新增内容 |

## 第 1 步：定体裁

动笔前回答三个问题：**读者是谁？读完要能做什么？读前读后的状态差在哪？**答案决定体裁，体裁决定详略。判断不了就问用户一次，不要猜。

| 体裁 | 读者时刻 | 骨架（按序） | 判生死的一条 |
|---|---|---|---|
| 札记（技术文档/梳理） | 几分钟建立心智模型 | 背景（2–4 行）→ 总图 → 机制节×N（按数据流）→ 场景×N | 读者能否拿文中样例值对着日志或代码验算 |
| 方案（设计文档） | 评审，要下判断 | 背景与问题 → 目标与**非目标** → 方案总览（图）→ 分述（按决策点）→ 备选与取舍 → 风险与验证 | 非目标和被否决项写了没有 |
| 教程（how-to） | 学习中，手把手 | 前置条件 → 目标成果 → 编号步骤（每步带验证点）→ 常见问题 → 下一步 | 干净环境照做能否一次成功 |

选定体裁后，**先读对应的 `references/genre-*.md` 再动笔**（每次只读选中的那一份）。

## 第 2 步：核对事实（动笔前，不省略）

文档的准确性靠这一步，不靠写得小心。工作方法：

1. **列出事实清单**：把文档将要声称的事实逐条列出——重点抓两类高危句：**数字**（间隔、上限、字节位、版本号）和**全称量词**（"所有""总是""唯一""必须"）。感觉越确定的句子越要核，确定感会短路核对。
2. **按源头分级取数**，每条事实只从唯一权威源取：

| 声明类型 | 唯一权威源 | 不可作源 |
|---|---|---|
| 系统行为 | 代码本身 + 运行观测 | 其他文档、自己的记忆 |
| 历史与决策 | commit message、ADR、评审记录 | 口口相传 |
| 协议约定 | proto 文件、后端接口文档、抓包 | 前端映射表里的注释 |
| 参数与常量 | 常量定义处 | 出现该常量的使用方 |

3. **证伪式核对**：对每条规则问"什么情况下它是错的？"，再到代码里找反例（如：某映射规律是否对所有条目成立）。
4. **三态标注**：事实 / 推断 / 示意 三种状态在文中可区分。示例值标"示意"；推断不写成断言；**无法核实的直接不写**（宁缺毋错——错的比缺的更糟，缺了会被问出来，错了会被信进去）。
5. **头部写事实基线**：对照的日期 + commit（如"2026-09-13 对照提交 `80f6bf473` 核对"），让读者知道信任半径。
6. 记住：**代码注释也只是提示，不是真相**。注释说 8 个市场、联合类型写着 9 个时，以代码为准。

## 第 3 步：排目录

目录是主线的投影。检验：**只读标题连起来，能听懂整篇讲什么、按什么顺序。**

- **两级封顶，7±2 节**（含场景节，一屏放得下）。内容装不下时拆文档（每个新文档重新定体裁），不加层级。
- **兄弟节颗粒一致、语法平行**：同一级标题同属一个缩放级别、同为名词短语。读者靠对称性建立速度预期。
- **标题即检索词**：领域术语必须出现在标题里；标题是一周后读者搜索的入口。
- **顺序跟随依赖**：每节只使用在它之前定义的概念；每节脱离上下文单独发给别人能看懂。
- **标题通读测试**：念给一个不懂该系统的人，能否复述出文档讲什么。通不过，回主线重排。
- 这个体量的文档**标题即目录**：不手写目录页，不写"附：文件索引/名词速查/函数速查"（静态索引默认腐烂，归宿是 ADR 和代码注释）。

## 第 4 步：成稿

**演优于讲。**机制用可执行痕迹承载——流程块、时序、决策表；散文只负责粘合。解说句（"X 是全体系的核心约束"）要求读者先把文字编译成心智模型，流程块直接给出模型。流程块自带三个红利：每个箭头是可证伪的断言、只有一条阅读顺序、嵌进样例值后读者可拿日志验算。

**规则嵌位，不开清单。**铁律写进它会被违反的那一步（改映射表的步骤里写该表的约束，而不是集中到"注意事项"节）。幸存的清单条目必须带后果——"否则订得上、收不到"是牙齿，没有后果的规则是考据。嵌位还包括负面指引："一般不用改 A / B / C"一行字，省掉乱改和瞎看。

**why 分级。**前提级 why（拿掉它方案看起来就是错的，如"差值时常数项抵消"）进正文；参数级 why（"心跳 20s 是 60s 的三分之一"）留在常量定义处即代码注释；历史级 why（为什么否决某备选）进 ADR 或 commit message。判据：读者缺了这条 why 会不会误推导或怀疑模型？不会，砍。

**语域。**标题与正文用专业名词、专业表达：禁疑问句、反问句（标题"斜率怎么算"应为"斜率递推"）；禁口语比喻（"两台计算器"应为"两套复权口径"；"先问锚点这单你能接吗"应为"先校验锚点可用性"）。生动的点睛句可以留在正文一句，不进标题。

**媒介默认值。**

- 图表优先 Mermaid，但**图要挣位置**：生命周期、分支判定、拓扑才画图；一行文字能说清的不画。总图全文唯一，紧跟背景、先于所有机制节；机制节内仅在结构确属二维时加局部图。
- **片段即证词**：先有论断后选片段，片段必须能证明其旁的论断，对不上就换片段或改论断。单段 ≤ 50 行（能短则短——长代码块是"讲"，拆出流程块才是"演"）。
- **片段必须自解释**（摘录脱离上下文，靠注释补足理解）：
  - 注释附着在被解释的代码行上，写「这一段在做什么、为什么」；来源定位写在片段前的正文里（如「入口：`protobuf/protocolbuf.ts`」），不写进片段头部注释；
  - 不复述代码（「// 设置最低价」是噪音）；源码自带注释原样保留，不叠加矛盾注释；
  - 省略显式标注（`// …` 或「节选有删改」），不静默截断；
  - 嵌入真实代码而非转述——转述会静默漂移，引用的片段会响亮地漂移（代码改了、文档没改，diff 立刻可见）；若需大量注释才可懂，说明选段不当：换更自解释的区间，或改为示意流程块。
- 行内定位只用「文件 + 符号名」，**禁止行号**（行号会腐烂，符号名不会）。
- 流程块里嵌**可验算的样例值**（如"收盘 = 398.50 + 增量"，随后给一行数值演算），可验算的例子是埋在文档里的测试用例。

**强调预算。**加粗只给不变量与后果；表格只给枚举；全是重点等于没有重点。

## 第 5 步：删减

用不对称账本逐句过：**这句话挂在读者的哪个动作上？**挂不上的删，删到疼为止。高频杂质清单：代码复读（读代码十秒能恢复的）、无后果的参数罗列、装饰性图表、同一事实的二次陈述、离题漂移（坑清单混进无关领域的问题）、静态索引、元信息超两行、导出噪音（多余分隔线、乱码实体——说明没有以读者身份重读过）。

删完后以**读者**（不是作者）身份通读一遍：每次"想往上翻"是结构信号（东西放错了位置），每次"这句在干嘛"是杂质信号（在讲而不是在演）。

## 第 6 步：发文前自检

依次过一遍，任何一条不过回去修：

1. 标题通读 = 一个完整的故事？
2. 全文一个体裁、一个阅读时刻？
3. 每句话挂在读者的动作上？能从代码十秒恢复的已删？
4. 图挣了位置且用 Mermaid？代码片段能证明其旁论断、单段 ≤ 50 行且自解释（行内解释注释到位、省略已标注）？无行号？
5. 规则都嵌进了会被违反的那一步？幸存清单条目都带后果？
6. why 分级归位（前提级在正文，参数/历史级回了家）？
7. 元信息 ≤ 2 行？无手写目录页、无静态索引表？
8. 高危句（数字、全称量词）逐条对到源头？头部有基线日期？示例值标了"示意"？
9. 运行符号巡检：`scripts/check_symbols.sh <文档路径> <仓库根>`（依赖 bash / git / grep / sed / find，Windows 下用 Git Bash；无 bash 环境时按脚本头部注释的逻辑人工核对）——对输出的 NOT FOUND 逐条判断：是概念词/仓库外引用则忽略，是真实符号名则修正文档或代码。
10. 若本篇与已有文档主题重叠：在新文档头部声明权威关系（"本文取代 X"），并同步在旧文档头部加被取代标注，或建议删除旧文档。一个主题只有一份正典。
