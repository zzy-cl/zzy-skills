# 札记（技术文档/梳理）深度指南

## 契约

读者要在几分钟内建立对系统的正确心智模型，并能在日后按需回来查铁律和操作场景。终点是：**读者拿文中少数几条生成规则（公理），能自己推导出未写的细节**——而不是记住全部细节。

## 骨架与要点

```
> 元信息 ≤ 2 行（基线日期 + commit；定位约定一句话）

## 背景            —— 2–4 行讲完问题，禁止铺垫
## <总图>          —— 全文唯一一张 mermaid 总图，紧跟背景
## <机制节 ×N>     —— 按数据流/时间流排列；每节 = 流程块 + 1–2 句粘合
## 场景：任务 A/B/C —— 手册部分，按影响范围递增排列
```

- **机制节**：每个环节一段代码块流程（伪代码 + 行内注释），节末落在"为什么"上（前提级 why）。概念不设节、不设表——概念从流程里长出来，首次出现时给一句话定义加英文对照。
- **场景节**：标题即任务（"场景：新增协议号（可参考已合入的 X）"）。步骤编号，约束嵌在步骤里；每篇场景给"一般不用动什么"的负面指引；场景间用边界引用互链（"出现独有协议时再按上一场景操作"），让读者不读无关部分。
- **排查入口**（日志开关、调试手段）只在场景或流程步骤里一行带过，不开独立章节。

## 该有的两个特征

1. **样例值可验算**：流程里的数字要能对日志、能手算（"15:00:04 推送原始价 402.50，增量 ≈ 0.53，图上收盘 399.03"）。
2. **边界嵌位**：适用范围（哪些市场/模式不覆盖）写进对应动作的位置（回退表、入口判断处），不设"已知局限"独立节——除非局限会改变读者对整个方案的判断。

## 已验证的反面形态

- 按代码模块切章节（"连接类要点 / useWs 与数据回写"实为文件目录镜像）——主线必须是数据流，不是代码结构。
- 概念表 + 递推规则表 + 流程图三件套讲同一件事——代码块行内注释就是表格，留一份即可。
- "已知限制/坑清单"独立成节且不带后果——嵌位到动作，或删。
- 心跳间隔、重连参数这类常数罗列——留在常量定义处。
