# 方案（设计文档）深度指南

## 契约

读者（评审人）要基于文档做同意/不同意的**判断**。方案文档给出判断所需的全部依据，仅此而已——它不是实现手册。它也是**有保质期的沟通工具**：服务于"达成共识"这个时刻，共识之后维护知识应流向 ADR、代码注释和常青文档，不背防腐的锅。

## 骨架与要点

```
## 背景与问题        —— SCQA：情境→冲突→问题→答案，四句话把评审人拉到与作者同一起点
## 目标与非目标      —— 非目标是全文含金量最高的段落：一句话省掉评审现场一半争论
## 方案总览          —— 一张 mermaid（拓扑/生命周期），先给地图再走路
## 方案分述          —— 按决策点或数据流组织，标题用短名词短语（即检索词，不编号）；每个决策点：做法 + 前提级 why + 关键代码片段(≤50 行)
## 备选方案与取舍    —— 被否决项必须写，否则三个月后有人原样重提
## 风险与验证        —— 影响面、回退路径、验证口径（怎么确认方案生效）
```

**骨架是查漏清单，不是排版模板。**六类内容（背景 / 非目标 / 总览 / 决策 / 备选 / 风险验证）必须被覆盖，但可以吸收为更小的容器——取舍表的一行「不做」、机制节里的后果句、结尾一段验证口径——不必各自成节；是否成节取决于该内容的重量。

## 关键规则

1. **非目标写具体**："本方案不依赖中台新增字段，前端单方面可落地""仅覆盖港股后复权，其他市场维持现状"——范围即承诺。可以是一张取舍表的「不做」行，不必独立成节。
2. **备选与被否决的 why 必写**，每项一句否决理由（不可行的原因/代价/时机）。已否决但远期可演进的方向标注"远期演进"，给未来留钩子。理由已在分述里讲过的，指向它即可，不复述。
3. **"为什么可行"用时序演**：把异步竞态、边界时序一步一步走给你看（"ACQUIRE 同步建连 → effect 订阅 → 未 OPEN 静默 → onopen 重放补发"），而不是"本方案解决了上述问题"这类自评句。
4. **风险写对策不写免责**：每条风险带触发条件 + 应对动作；已知限制诚实标注（哪些场景未覆盖、为什么门控能覆盖）。
5. **验证口径可执行**：typecheck/lint 之外，需要真机/真数据确认的场景逐条可勾（清单或「核对块 → 预期」表），并覆盖关键状态组合（如未购/已购两种权益态）。

## 事实纪律

- 方案里的"现状描述"（老逻辑怎么运作、问题怎么产生）同样要按源头核对——现状错了，整个论证塌掉。
- 性能/量级声明（"约 220KB""收益大一个量级"）给出测量口径或标注估算。
